# Decisões Técnicas do NPSharp\n\n## Visão Geral\n\nEste documento registra as decisões arquiteturais, padrões e trade-offs identificados no código do NPSharp. Onde não há certeza sobre a origem, é anotado como \"inferido pelo código\".\n\n## 1. Escolha de Framework UI: JavaFX\n\n### Decisão\nUsar JavaFX 21.0.2 como framework de interface gráfica.\n\n### Alternativas Consideradas\n- Swing (legado Java)\n- SWT (Eclipse)\n- Electron/Web (Node.js)\n- Qt (C++)\n\n### Vantagens\n- **Nativa Java** - Integração direta, sem wrapper\n- **Moderna** - CSS support, GPU acceleration\n- **Cross-platform** - Windows, Linux, macOS com mesmo código\n- **Performance** - Melhor que Swing, próxima ao C++\n- **Comunidade** - Ativa, muita documentação\n- **VS Code Look** - Possível replicar design do VS Code\n\n### Desvantagens\n- **Menor comunidade que Electron** - Menos plugins/templates\n- **Curva de aprendizado** - Diferente de web frameworks\n- **Size bundle** - JavaFX + JVM é ~200MB\n- **Startup time** - Mais lento que aplicação C++\n\n### Decisão Inferida\nEscolhido para manter tudo em Java/Maven, facilitando contribuições de devs Java.\n\n---\n\n## 2. Sistema de Build: Maven\n\n### Decisão\nUsar Maven 3.8+ para gerenciamento de dependências e build.\n\n### Alternativas\n- Gradle\n- Ant\n- Mill\n- Bazel\n\n### Vantagens\n- **Padrão enterprise** - Amplamente adotado\n- **Reproducible builds** - Mesmo resultado dado mesmas dependências\n- **Plugins ricos** - maven-compiler-plugin, maven-shade-plugin, etc.\n- **Convention over configuration** - Menos boilerplate\n- **CI/CD ready** - Integração fácil com Jenkins, GitLab CI, etc.\n\n### Desvantagens\n- **XML verbose** - pom.xml pode ficar grande\n- **Menos flexível** - Gradle oferece mais controle programático\n- **Velocidade** - Gradle é mais rápido em builds incrementais\n\n### Decisão Inferida\nEscolhido pela simplicidade, standardização e integração com ecossistema Java corporativo.\n\n---\n\n## 3. Async Pattern: CompletableFuture\n\n### Decisão\nUsar `CompletableFuture<T>` para operações assíncronas (Git, Debug, Search).\n\n### Código Exemplo\n```java\n// GitService.java\npublic CompletableFuture<List<GitRepositoryStatus>> statusAsync(File workspace) {\n    return CompletableFuture.supplyAsync(\n        () -> discoverRepositories(workspace),\n        executor  // ExecutorService com thread pool\n    );\n}\n```\n\n### Alternativas\n- Callbacks\n- Reactive Streams (Project Reactor)\n- Virtual threads (Java 21+, preview)\n- Rx-Java\n\n### Vantagens\n- **Built-in Java** - Parte de java.util.concurrent\n- **Composable** - `.thenApply()`, `.thenCompose()`, etc.\n- **Cancelable** - `.cancel()` interrompe operação\n- **UI-safe** - `.thenRunOnFxThread()` dispara callback na FX thread\n- **Error handling** - `.handle()`, `.exceptionally()`\n\n### Por que não Callbacks?\n- **Callback hell** - Nested callbacks são ilegíveis\n- **Error propagation** - Difícil propagar erros\n- **Composição** - Não é possível combinar múltiplas operações\n\n### Por que não Reactive Streams?\n- **Overhead** - Adiciona dependência (Project Reactor, RxJava)\n- **Overkill** - NPSharp não faz processamento de stream contínuo\n- **Curva de aprendizado** - CompletableFuture é mais simples\n\n### Decisão Inferida\nCompletableFuture oferece bom balanço entre simplicidade e poder sem dependências adicionais.\n\n---\n\n## 4. Persistência de Configurações: JSON\n\n### Decisão\nUsar JSON (via Gson) para persistir settings em `~/.npsharp/settings.json`.\n\n### Código\n```java\n// SettingsService.java\nprivate final Path settingsPath = Path.of(\n    System.getProperty(\"user.home\"),\n    \".npsharp\",\n    \"settings.json\"\n);\n```\n\n### Alternativas\n- Properties files (.properties)\n- YAML\n- XML\n- SQLite database\n- Prefs API (java.util.prefs)\n\n### Vantagens\n- **Legível** - Humano e máquina leem bem\n- **Sem dependência** - Gson está no projeto já\n- **Estruturado** - Hierarquias complexas\n- **Standard** - Muitas ferramentas entendem JSON\n- **Editável** - Usuário pode editar manualmente se necessário\n\n### Por que não Properties?\n- **Flat structure** - Não suporta hierarquias bem\n- **Verbose** - Muita repetição\n- **Tipagem** - Tudo é string, requer parsing manual\n\n### Por que não SQLite?\n- **Overkill** - Settings simples não precisam de DB\n- **Dependência** - Adiciona complexidade\n- **Overhead** - Inicializar conexão é caro\n- **Portabilidade** - JSON é mais portável\n\n### Decisão Inferida\nJSON oferece bom balanço entre simplicidade, legibilidade e estrutura sem overhead de banco de dados.\n\n---\n\n## 5. Editor de Texto: RichTextFX\n\n### Decisão\nUsar RichTextFX 0.11.3 para `CodeArea` em vez de implementar do zero.\n\n### Benefícios\n- **Syntax highlighting** - Já implementado\n- **Performance** - Virtualized scrolling\n- **Estável** - Projeto maduro\n- **Customizável** - Estilos, fonts, behaviors\n\n### Código\n```java\n// EditorManager.java\nCodeArea editor = new CodeArea();\nVirtualizedScrollPane scrollPane = new VirtualizedScrollPane<>(editor);\n```\n\n### Trade-offs\n- **Não é VS Code** - Mas nenhuma library o é\n- **Limitações** - Alguns features (minimap, folding) seria custom\n- **Depêndência** - RichTextFX pode ficar inativa\n\n### Decisão Inferida\nMelhor usar library pronta do que reimplementar editor. Futuro pode migrar para outra se necessário.\n\n---\n\n## 6. Git Integration: Executar Git via CLI\n\n### Decisão\nInvoca `git` comando CLI (ProcessBuilder) em vez de usar library Git.\n\n### Código\n```java\n// GitService.java\nProcessBuilder pb = new ProcessBuilder(gitExecutable, ...args);\nProcess process = pb.start();\nprocess.waitFor();\n```\n\n### Alternativas\n- JGit (library Git em Java)\n- Eclipse JGit\n- Gitpython via JNI\n\n### Vantagens\n- **Sem dependência** - Git já instalado localmente\n- **Sempre sincronizado** - Usa versão installed do Git\n- **Simples** - Invoke CLI é trivial\n- **Confiável** - Git CLI é battle-tested\n\n### Desvantagens\n- **Performance** - Spawn de processo é mais caro\n- **Parsing** - Saída CLI muda entre versões\n- **Plataforma** - Path de Git diferente (Windows vs Linux)\n\n### Por que não JGit?\n- **Dependência pesada** - Adiciona 5+MB\n- **Comportamento diferente** - Pode divergir do Git\n- **Maintenance** - Se JGit ficar obsoleto, problema\n- **Features** - Git tem features que JGit não implementa\n\n### Decisão Inferida\nCLI é mais simples e confiável. Performance é aceitável para operações Git.\n\n---\n\n## 7. Tema: JSON + CSS Dinâmico\n\n### Decisão\nCarregar temas de JSON (compatível VS Code) e aplicar via CSS dinâmico em runtime.\n\n### Código\n```java\n// ThemeManager.java\nVSCodeThemePackage theme = themeRegistry.get(themeName);\nEditorTheme editorTheme = new EditorTheme(theme);\nString css = CSSThemeGenerator.generate(editorTheme);\nscene.getStylesheets().add(css);  // Aplicar dinamicamente\n```\n\n### Vantagens\n- **VS Code compatible** - Importar temas VS Code diretamente\n- **Runtime changeable** - Trocar tema sem reiniciar\n- **Sem recompile** - Temas são dados, não código\n- **User extensible** - Usuário cria novos temas\n\n### Desvantagens\n- **Performance** - Parsing JSON + CSS generation tem custo\n- **Validação** - Possível JSON inválido\n- **Debugging** - CSS gerado dinamicamente é difícil debugar\n\n### Decisão Inferida\nJSON + CSS dinâmico é necessário para trocar temas em runtime sem reiniciar aplicação.\n\n---\n\n## 8. Padrão Singleton para Serviços\n\n### Decisão\nServiços de sistema são singletons (`SettingsService.getInstance()`).\n\n### Código\n```java\npublic final class SettingsService {\n    private static final SettingsService INSTANCE = new SettingsService();\n    \n    public static SettingsService getInstance() {\n        return INSTANCE;\n    }\n}\n```\n\n### Alternativas\n- Dependency Injection (Spring, Guice)\n- Service Locator\n- Factory Pattern\n\n### Vantagens\n- **Simples** - Sem framework adicional\n- **Global** - Acesso de qualquer lugar\n- **Lazy loading** - Inicializado só quando necessário\n- **Único estado** - Uma instância = um estado\n\n### Desvantagens\n- **Threading** - Singletons não são thread-safe por padrão\n- **Testabilidade** - Difícil mockar em testes\n- **Hidden dependencies** - Classe depende de singleton implicitamente\n- **Static state** - Acoplamento global\n\n### Por que não Dependency Injection?\n- **Overhead** - Spring é pesado para desktop app\n- **Complexidade** - XML/annotations adiciona boilerplate\n- **Startup** - Spring scan classes é lento\n- **Já funciona** - Singleton é suficiente para NPSharp scale\n\n### Decisão Inferida\nSingleton é pragmático para aplicação desktop. Futuro pode refatorar com DI se escalar.\n\n---\n\n## 9. Runtimes: Registry + Dynamic Installation\n\n### Decisão\nManter registry de runtimes instalados em `runtime-registry.properties` e permitir detecção automática.\n\n### Código\n```java\n// RuntimeRegistry.java\nprivate final Map<LanguageRuntime, InstalledRuntime> installed = \n    new EnumMap<>(LanguageRuntime.class);\n```\n\n### Vantagens\n- **Flexível** - Suporta múltiplas versões de mesmo runtime\n- **Portável** - Arquivo é simples properties\n- **Descoberta** - Auto-detecta runtimes instalados\n- **Gerenciável** - Usuário pode editar manualmente se necessário\n\n### Decisão Inferida\nRegistry permite debug/edit manual se necessário, sem perder flexibilidade.\n\n---\n\n## 10. Busca: Paralelo + Streaming\n\n### Decisão\nUsar `Stream.parallel()` para processamento paralelo na busca de workspace.\n\n### Código\n```java\n// WorkspaceSearchService.java\ntry (Stream<Path> stream = Files.walk(workspaceRoot)) {\n    stream.parallel()  // Parallelização automática\n        .filter(Files::isRegularFile)\n        .filter(this::isSearchableFile)\n        .forEach(path -> search(path, query, results));\n}\n```\n\n### Trade-offs\n- **Vantagem** - Usa múltiplos cores do CPU\n- **Overhead** - Synchronization tem custo\n- **Unprevisível** - Ordem de resultados varia\n- **Memory** - Stream paralelo usa mais memória\n\n### Limite de Resultados\n```java\nprivate static final int MAX_RESULTS = 5000;  // Previne memory exhaustion\n```\n\n### Decisão Inferida\nParalelização é necessária para busca performance. Limite previne problemas de memória.\n\n---\n\n## 11. Diagnostics: Compilação em Background\n\n### Decisão\nExecutar compilação (Maven/Gradle) em thread separada durante edição.\n\n### Benefícios\n- **Não bloqueia UI** - Usuário continua digitando\n- **Feedback em tempo real** - Erros aparecem inline\n- **Auto-save ready** - Pode compilar automatically\n\n### Implementação\n```java\n// EditorDiagnosticsManager.java\nExecutorService executor = Executors.newSingleThreadExecutor();\nexecutor.submit(() -> {\n    runDiagnostics();\n});\n```\n\n### Decisão Inferida\nBackground compilation é essencial para editor moderno.\n\n---\n\n## 12. File System Abstraction\n\n### Decisão\nInterface `FileSystemProvider` abstrai arquivo local vs remoto.\n\n### Código\n```java\npublic interface FileSystemProvider {\n    List<Path> list(Path dir);\n    byte[] read(Path file);\n    void write(Path file, byte[] content);\n}\n```\n\n### Implementações\n- `LocalFileSystemProvider` - Filesystem local\n- `RemoteFileSystemProvider` - Via SSH\n\n### Vantagens\n- **Extensível** - Fácil adicionar novo provider\n- **Clean separation** - UI não sabe se é local ou remoto\n- **Futura** - Pode adicionar S3, Google Drive, etc.\n\n### Decisão Inferida\nAbstração permite suporte a múltiplos filesystems sem duplicação de código.\n\n---\n\n## 13. Atalhos: Interceptor Global\n\n### Decisão\nInterceptar `KeyEvent` globalmente na Scene para processar shortcuts.\n\n### Código\n```java\n// ShortcutManager.java\nscene.setOnKeyPressed(event -> {\n    if (event.isControlDown() && event.getCode() == KeyCode.S) {\n        editorManager.save();\n        event.consume();  // Previne propagação\n    }\n});\n```\n\n### Alternativas\n- Event handlers em cada componente\n- Accelerators (JavaFX built-in)\n\n### Vantagens\n- **Centralizado** - Um lugar para gerenciar todos\n- **Consistente** - Mesmo atalho em qualquer lugar da app\n- **Interceptável** - Pode loggar/debuggar/remapear\n\n### Decisão Inferida\nInterceptor global é padrão para apps desktop.\n\n---\n\n## 14. Linguagem: Java 17+\n\n### Decisão\nUsar Java 17+ com features como:\n- Records\n- Sealed classes\n- Pattern matching (preview)\n- Text blocks\n\n### Vantagens\n- **Moderno** - Features recentes melhoram código\n- **Performance** - JVM otimizações contínuas\n- **LTS** - Java 17 é Long Term Support\n- **Segurança** - Updates regulares\n\n### Desvantagens\n- **Compatibilidade** - Requer JDK 17+, não roda em Java 11\n- **Dependência** - Acoplado a evolução Java\n\n### Decisão Inferida\nJava 17+ oferece linguagem mais expressiva e performance melhorada. Worth o requerimento.\n\n---\n\n## 15. Estrutura de Pacotes: Por Camada + Feature\n\n### Decisão\nOrganizar código por:\n1. **Camada** - frontend vs backend\n2. **Feature** - editor, terminal, git, etc.\n\n### Estrutura\n```\nfrontend/\n  ui/\n    editor/\n    terminal/\n    theme/\n    ...\n  settings/\n  \nbackend/\n  git/\n  debugger/\n  runtime/\n  filesystem/\n  ...\n```\n\n### Alternativas\n- Por funcionalidade pura (editor/, search/, etc.)\n- Por domínio (user/, project/, file/, etc.)\n\n### Vantagens\n- **Separação clara** - Frontend vs backend\n- **Escalável** - Fácil adicionar novo feature\n- **Evita ciclos** - backend não depende de frontend\n\n### Decisão Inferida\nSeparação por camada + feature é padrão em apps enterprise.\n\n---\n\n## Resumo de Trade-offs\n\n| Decisão | Trade-off | Aceitável |\n|---------|-----------|----------|\n| JavaFX | Size bundle (200MB) | ✅ Aceitável para desktop |\n| Maven | XML verbose | ✅ Padrão enterprise |\n| CompletableFuture | Menos funcional que Reactive | ✅ Simples suficiente |\n| Singleton | Testabilidade | ✅ Suficiente para app scale |\n| Git CLI | Performance | ✅ Operações Git são raras |\n| JSON Themes | Parsing overhead | ✅ Necessário para mudança dinâmica |\n| Java 17+ | Requer newer JDK | ✅ LTS, suportado até 2029 |\n\n---\n\n## Potenciais Refactorings Futuros\n\n1. **Dependency Injection** - Se aplicação crescer muito\n2. **Plugin Architecture** - Para extensões de terceiros\n3. **Virtual Threads (Java 21)** - Para melhor async\n4. **Modular System** - Para separação mais clara\n5. **Event Bus** - Para comunicação entre componentes\n\n---\n\n**Última atualização:** 2026-07-02\n
